# dsh-tool-token-optimizer —— 工具调用联动 token 的极致压缩

> 一句话：**在工具结果落盘之前把它改小**——能无损压缩的无损压缩，压不动的按预算保留
> 「头 + 尾 + 全部报错行」，并给出一行精确的取回路径。信息不丢，token 大降。

## 实测数据（本机 25 个真实会话、2596 条真实工具结果）

| 指标 | 数值 |
|---|---|
| 工具结果 token | 1,234,957 → 388,740（**省 68.5%**） |
| 被改动的结果条数 | 678 / 2596（26.1%），其余 **73.9% 逐字节不动** |
| 全表面反事实回放（2138 次真实请求，含系统提示、历史与工具表） | 3.696 亿 → 2.689 亿（**省 27.3%**） |
| 单会话省量中位数 | **36.4%**（p25 7.6%，p75 41.8%） |
| 单条开销 | 平均 **0.059 ms**、P95 0.242 ms；1.2 MB/4 万行输入 30 ms |
| 测试 | **96 项全部通过**（含 2596 条真实语料的不变量、上界与保真验证） |

> 下面这条"硬约束"清单是这份 README 里最该先看的部分——它们都曾经被违反过：
>
> 1. **`inlineChars` 是上界**：实测语料 625 条被裁剪的结果里，**0 个文本块超过 1600 字符**
>    （修复前 143/625 超标，最大 1.31 倍）；
> 2. **末行（结论、退出状态）永不消失**：末单元即使自己超过整个尾部预算，也退化为
>    「截断 + `…[line clipped]` 标记」，而不是被中段填充物挤掉（修复前 30/677 条丢掉原文末行）；
> 3. **真实失败信号不漏检**：`AssertionError`、`npm ERR!`、`Expected:/received:`、`✗`
>    这类此前漏检的形态已全部纳入（`✗` 曾因 `\b` 断言在非单词字符上不成立而整片漏掉）；
> 4. **说明行的数字可核对**：`omitted chars + 成品长度 == of N` 在最终交付的文本上精确成立，
>    且 `of N` 是**无损层之前**的原文长度。

省下的是**每一次后续请求都要重发的历史**，因此一条结果被压缩后省量随会话推进不断累加；
而压缩只在结果生成那一刻执行一次，前缀缓存（`cacheReadTokens`）完全不受影响。
完整可复现记录见 [`docs/MEASUREMENTS.md`](docs/MEASUREMENTS.md)。

## 1. 设计的第一原则：为什么只能在这一刻压缩

DSH 的请求前缀完全依赖 provider 侧的前缀复用，真实会话里 `cacheReadTokens` 通常占总输入的
七到九成，且按缓存命中价计费。任何对**已经发出去过**的消息的改写，都会让从改动点往后的
整段前缀作废——省下的那点 token 会以数倍的重新计价还回去。

因此本插件的边界是硬的：

- **只挂在 `tools/post-execute`**，改的是尚未进入请求的那一条结果；
- 绝不触碰历史消息、绝不按轮次增删工具表、绝不改系统提示的静态部分；
- **不做**跨结果的“引用前文”式压缩（前置结果一旦被折叠或剪枝，引用即失效）；
- 挂在 Host 根部并 `prepend: true`，`await next()` 之后才决策，因此看到的是所有下游
  转换器（官方 `spill-policy`、`fs-search` 的溢出替换等）处理完的**最终内容**。

官方 `dsh-compaction-tool-result-pruner` 走的是另一条路（上下文压力触发时替换旧节点）。
两者互补：本插件让“写得进上下文的结果更小”，官方剪枝让“已经堆满的上下文更短”。

## 2. 压缩管线

### 2.1 无损规范化（`lib/text.js`）——每一步都可逆

| 变换 | 做什么 | 为什么无损 |
|---|---|---|
| `newlines` | `\r\n` → `\n`，删除裸 `\r` | 裸 `\r` 是终端覆盖写：后面紧跟的内容会原地覆盖前面的内容，删掉后剩下的正是终端最终显示的那一版 |
| `trailing-spaces` | 删除每行行尾空格/制表符 | 行尾空白在任何解析器里都不带语义 |
| `blank-padding` | 只由空白组成的行清空内容 | 不删换行，行号与后续内容位置完全不变 |
| `blank-runs` | 4 个以上连续换行折成 3 个 | 2 个空行与 3 个以上空行语义等价（都只表示段落边界） |
| `duplicate-runs` | 连续 N（≥3）行相同 → 首行 + `⟨dup ×N⟩` | 折叠次数写回文本，可精确还原；标记加在首行之后，行号不漂移 |

每一步之后都有**净收益闸门**：只要不比原文小，就整段丢弃这次变换——插件永远不会把结果
改得更贵。真实语料里这一步贡献有限（54 条结果、约 2.5k token），它的价值在于**零风险地
吃掉噪声**，而不是当主力。

### 2.2 有界保留（`lib/retain.js`）——真正的省量来源（99.7%）

超过内联预算（默认 1600 字符）时保留：

1. **头部**（预算的 55%）：格式、接口、命令回显、匹配计数头部；
2. **尾部**（35%，且不少于 300 字符）：结论、报错、退出状态，以及 DSH 自己写的可恢复路径
   （`[output truncated; full output: …]`、`Full formatted result stored at: …`、grep/glob 的
   `Full … result stored at: …`）；
3. **全部可疑行**（预算的 40%，不少于 400 字符）：错误/失败/警告/堆栈/`[exit code: N]`，
   按“越靠近尾部越优先”占用额度。

中段替换为一行说明：

```
[…] omitted 128443 chars / 812 lines of 201337; 3 error/warning lines were in the omitted middle;
re-run this command (optionally piped) to see any range
```

说明同时给出**省掉了多少**、**里面有几行报错**、**怎么取回**——三者缺一，模型就会重跑工具，
省下的 token 又花回去。取回方式用的是**这次调用参数里本来就有**的动作：

| 工具 | 取回提示 |
|---|---|
| `bash` / `pwsh` | re-run this command (optionally piped) to see any range |
| `read` | re-read with offset/limit to see any range |
| `grep` | narrow the pattern or path to see any range |
| `web_fetch` | fetch a more specific URL to see any range |
| `cordis_inspect_query` | query the exact Service/Event/entry to see any range |
| … | 其余工具走 `re-run <tool> to see any range` |

### 2.3 结构感知裁剪：按结果自身的边界切，不切进行中间

早期版本按**字符位置**切头尾。真实输出本身是有结构的，按字符切会：

- 把某一行**劈成两半**（模型看到半行，且"丢弃了多少行"无法精确计数）；
- 把 `bash` 的 `[stderr]` 段与 stdout 任意切开（可能看到 `[stderr]` 标题却没有正文）；
- 把 `grep` 的**整个文件分组**丢掉（"某个文件到底匹配了没有"是离散信息，丢了比丢几行更糟）。

现在 `lib/sections.js` 把结果切成**单元**，只在单元边界取舍：

| 结果类型 | 切分方式 |
|---|---|
| `bash` / `pwsh` / `job_*` | 按 `[stderr]` 行与状态标记行（`[exit code: N]`、`[timed out…]`、`[killed by signal…]`）分节 |
| `grep` | `Found N matches` 头部 + 每个文件一组 + 取回提示行，各自成单元 |
| 其它 | 一行一单元 |
| 单行本身超预算 | **唯一**允许硬切的情形（没有行结构可言的机器输出） |

三条保证，全部由测试锁死：

1. **只在行边界断开**：单元可以略超尺寸上限，也绝不把一行劈开
   （`test/sections.test.js` + 语料级用例：623 条被裁剪结果逐条核对，23 条单行块按例外处理）；
2. **`[stderr]` 与状态标记是独立单元且优先级最高**：要么完整保留，要么被精确计数说明；
3. **说明里的数字是真话**：`lines` / `chars` 都按"实际未被保留的单元"统计，且扣除被补回内联的可疑行。

代价：**省量几乎不变**（62.79% → **62.77%**，连跑三次结果逐字节相同，差异来自行边界吸附多吃的几个字符），
换来的是"模型看到的是完整行与完整分组"。

### 2.5 针对性审计：被省略的中段到底丢了什么

对全部 623 条被裁剪的真实结果做了一次逐项核对，问的是同一个问题：**“模型要继续做下去所需
的信息，还在不在？”**

| 检查项 | 结果 |
|---|---|
| `read` 的 `<path>` 信封与续读 footer（`Showing lines A-B of N. Use offset=…`） | 0 丢失 |
| `grep` 的 `Found N matches` 头部与文件路径行 | 0 丢失 |
| `[exit code: N]` | 0 丢失 |
| `[output truncated; full output: …]` / `Full … result stored at: …` | 0 丢失 |
| DSH 结构标记行（`[stderr]`、`[timed out…]`、`[killed by signal…]`、`[…]` 提示等） | 118/118 保留 |

审计中唯一一次“看起来丢了”的情况，是某条 `bash` 结果里**引用了另一个工具的 spill 文本**，
其文件名恰好也被本插件的说明行引用——属于假阳性。为了让 `[stderr]` 这类**分节标记**永不落进
中段（丢了它，一段警告会和 stdout 混在一起被误读），已把这类标记行加入“可疑行”集合，
并被 `test/corpus.test.js` 的专门用例锁住。

### 2.6 永不触碰的东西

- **失败结果**（`isError`）：一个字都不动——那是模型自我纠错的唯一依据；
- **富内容块**（图片、文件块）：不参与裁剪判定，也不会被删除；
- **下游已替换成结构化 `value` 的结果**：那不是文本结果，无权改动；
- **下游 `block` 决策**：原样透传，其它决策字段（如 `additionalContexts`）保留。

### 2.7 行为对照实验：裁剪会不会改变模型的结论

「信息守恒」不等于「行为等价」。为此做了一次真实模型的 A/B 对照（`docs/AB-EXPERIMENT.md`）：

**第二轮（正式对照）**：8 个任务（含 2 道"答案只存在于被省略中段"的针任务、2 个含干扰行的陷阱）、
两条件、共 16 次真实运行、`tools/ab-score.mjs` 自动判分：

| | 对照（插件关闭） | 实验（插件启用） |
|---|---|---|
| 正确率 | **8/8（100%）** | **8/8（100%）** |
| 逐题判定 | \multicolumn{2}{c}{**完全一致，含两道中段针任务**} |
| **未命中 / 请求**（插件的作用点） | 322 | **222（−31%）** |
| 按价折算成本 | ￥0.0221 | **￥0.0205（−7.1%）** |
| prompt 合计（错误口径，受请求数影响） | 474,066 | 537,214 |

**第三轮（成本专项，5×2 重复）**：内容规模放大 **12.4 倍**（14.8K → 183K 字符，后者触发裁剪），
各跑 5 次：**未命中/请求 344 → 245（−29%）、按价成本 ￥0.00286 → ￥0.00245（−14%）**，
而**正确率都是 5/5**。即"大 12.4 倍的文件，成本反而更低"。

**第一轮（早期探针）**：真实任务 42/42 对 42/42 逐项一致；强制只读一次的针任务如实回答
`NOT_VISIBLE`；允许取回时用 30 次 offset/limit 续读正确定位，但累计 105k token 比一次读全的 68.9k 更贵——
**这暴露了"取回必然便宜"的假设不成立**，详见 [`docs/AB-EXPERIMENT.md`](docs/AB-EXPERIMENT.md)。

结论：**对不需要中段的任务没有可测量的质量差异；对"中段里正好有唯一答案"的任务会多付一次取回成本**，
而且实测这次取回（105k token）比原本一次读全（68.9k）更贵——**"取回很便宜"这个假设不完全成立**，
已知的改进方向记在实验报告里，但未擅自改默认值。

### 2.8 评估后**放弃**的优化（以及为什么）

| 候选 | 为什么不采用 |
|---|---|
| 对 minified JSON 断行/缩进 | 实测断行让长度 **+5%**（换行本身占字符，空白 token 化后并不省），净收益闸门会整段拒绝 |
| 跨结果重复内容去重（引用前文） | 真实语料里逐字重复只占工具结果字符的 **0.7%**；且前置结果被剪枝后引用即失效，风险远大于收益 |
| 改写已入历史的旧结果 | 直接击穿前缀缓存，省 1 份要赔数份 |
| 删除 `read` 的行号前缀 | 行号是 `edit` 与“第几行有问题”的坐标，删掉会改变模型行为（涉及约 14% 的结果 token），属于**降低质量** |
| 自动把 `ls -la` 转成紧凑格式 | 会丢掉权限位/大小/时间戳；重跑一次 `stat` 的成本高于省下的量 |
| 改写系统提示 / 工具表 | 那是能力面与指令面，改了就改变输出质量，越界 |

## 3. 作用域：为什么它自己会给每个 agent 装一份

`tools/post-execute` 由 `ToolRuntime` 以 **agent 作用域**派发（`scopeTarget(this, exec.agent)`）。
DSH 的 agent 作用域是 `ctx.isolate()` 出来的**完全隔离**作用域，与 profile 根之间没有父子
关系；作用域过滤器只放行「无标签」或「派发键自身及其祖先」的监听器。因此在 profile 根上
注册的监听器**收不到** agent 作用域的事件——本机实测：挂在根的插件行会长期停在
`fiberPhase: failed`，监听器从不触发（这也是官方把 `dsh-spill-policy`、`fs-search`、
`repeat-tool-reminder` 的注册行写进 **preset** 的原因）。

本插件让用户不必改任何预设，自己完成了等价的事：

1. 根上 `inject: ['agents']`，等 agents 注册表就绪；
2. 监听 `agent/created`，对每个 agent 在**它自己的 context** 上 `inject(['tools'], …)`，
   并在该作用域注册监听器（fiber 归属该 agent，agent 释放即自动卸载；热重载时会对
   已存在的 agent 补装）；
3. 根上另注册一份，覆盖非 agent 作用域的工具执行。

两处注册共用同一个处理器，按结果对象身份用 `WeakSet` 记账，保证一条结果只压缩一次。

## 4. 缓存命中率：实测与边界

用户要求「缓存命中率优化到极致、至少 95%」。先把口径说清楚：
`命中率 = cacheReadTokens / (cacheReadTokens + inputTokens)`，两个数都来自 provider 返回的
usage，因此这不是估算。**这个指标不由插件直接决定**，它由「前缀是否稳定」决定，而
前缀 = 系统提示 + 工具表 + 历史消息。

### 4.1 实测（22 个真实会话、2136 次请求）

| 指标 | 数值 |
|---|---|
| 整体命中率 | **99.07%**（cacheRead 4.09 亿 / 未命中输入 386 万） |
| 达到 95% 的会话 | 15 / 22 |
| 未命中构成 | 前缀作废 **37.4%**、每会话首请求 **1.8%**、其余为逐次新增内容的固有未命中 |
| **本会话（插件生效后）** | 335 次请求，命中率 **99.73%**，前缀作废 **0 次** |

### 4.2 前缀稳定性：逐字节验证，不是推断

对 2136 次请求重建「实际发出去的表面」，逐字节比较相邻两次请求：

| 相邻请求关系 | 次数 |
|---|---|
| **纯追加**（前一次的表面是新表面的前缀） | **2110** |
| 更早的内容被改写 | 1 |
| 工具表变化 | 3 |

即 **98.8% 的请求是纯追加**——这是缓存命中率能到 99% 的根本原因，也说明插件所在的这一层
（结果落盘）本来就是缓存安全的。剩下 1 次内容改写与 3 次工具表变化，全部对应
`request/header reason=change|resume`（系统提示/工具面变化），属于**刻意改变行为**才会发生的事，
不是噪声。

### 4.3 插件对这一指标的三个保证（`test/cache.test.js` 锁定）

1. **前缀不变性**：只挂 `tools/post-execute` 与 `agent/created`，**不注册任何 system-prompt /
   request / tool-schema 钩子**，因此已缓存前缀永远有效——测试直接断言监听器集合就是这个两条。
2. **确定性**：同一内容重复处理 8 次、穿插其它结果后再处理、6 路并发处理，输出逐字节相同。
   前缀复用要求「同一前缀逐字节相同」，任何时间/顺序/并发相关的抖动都会击穿缓存，这里没有。
3. **只减不增**：真发生前缀作废时，需要重新计价的正是**工具结果**——它已经小了
   **68.5%**（1,234,957 → 388,740 token）。也就是说插件把「缓存失效的代价」本身也压低了。

### 4.4 剩下 5% 在哪，以及为什么不该由插件去动

- **深会话天然 ≥99%**：每次请求新增内容约 250–800 token，其中约 256 是缓存块粒度造成的
  固有未命中，与插件无关；
- **短会话（≤6 请求）必然 <95%**：首请求 1.3k–8.3k token 全 miss，摊不开。想「优化」它只能砍
  系统提示或工具表——那会改变能力面与输出质量，属于越界，本插件不做；
- **`reason=change` 的作废**是一次性成本，且下一次请求立刻重新缓存（实测紧跟的 ΔcacheRead 为正）。

结论：**在质量不变的前提下，命中率的极致就是「不碰前缀 + 让新增内容尽量小」，插件两点都做到了。**

## 5. 性能：单条结果上增加多少开销

插件的全部运行时成本只有一处：结果落盘**之前**在内存里跑一遍纯函数。**没有 I/O、没有
网络、没有子进程、没有额外的模型请求**，也不会有任何后台工作。实测（`node tools/bench.mjs`）：

| 指标 | 数值 |
|---|---|
| 真实语料单条 **平均** | **0.036 ms** |
| 单条 P50 / P95 / P99 / 最大 | 0.004 / 0.134 / 0.520 / **3.526 ms** |
| 每 KB 耗时（线性） | 约 **0.02 ms/KB**（0–512 字符 0.0127、32k+ 字符 0.0241，未随规模恶化） |
| 极端情况：40k 行 / 1.2 MB 文本 | 17.5 ms |
| 极端情况：10 万行重复行 / 2.5 MB | 6.6 ms |
| 5.2 万次压缩连跑 | 1670 ms，平均 0.032 ms/条，堆内存无累积 |

对比 DSH 工具调用基线：一次本地 `bash` 命令（进程启动 + 执行）约 **5–20 ms 起**，
一次 `read` 约 1–5 ms，一次 `web` 请求数百 ms。**插件单条平均开销比最便宜的工具调用还低
一个数量级以上**，而且是异步 waterfall 里的同步计算，不引入额外等待。

> 换句话说：它不会让会话变慢。真正决定延迟的是模型推理与工具本身的执行时间；插件对
> 这两者都没有影响，也不改变模型的输出（它只改“工具已经算完的结果怎么摆”）。

## 6. 安装

本包是一个 **bundle**（`package.json` 里 `dsh.bundle.patch` 指向 `cordis.patch.yml`），
补丁只插入一行 `tool-token-optimizer`，挂在 Host 根部。

```bash
# 方式一：从 tarball 安装（推荐，profile 侧不需要构建）
dsh plugin install file:/绝对路径/dsh-tool-token-optimizer-1.0.0.tgz

# 方式二：从源码目录安装（开发时可改完即生效）
dsh plugin install link:/绝对路径/dsh-tool-token-optimizer
```

或在 GUI 里用 `plugin_manager` 工具的 `install_bundle`，`target` 填同一个 spec。
安装后 `dsh.profile.bundles` 会多出 `dsh-tool-token-optimizer` 一项；重启宿主后生效。

**回滚**：把该 bundle 从 profile 的 `dsh.profile.bundles` 移除，或把补丁里那一行的
`disabled` 设为 `true`。

## 7. 配置

`cordis.patch.yml` 里的默认值：

| 键 | 默认 | 含义 |
|---|---|---|
| `enabled` | `true` | 总开关。`false` 时连监听器都不装，结果与优化前**逐字节一致**（用于 A/B 对照或临时停用） |
| `inlineChars` | `1600` | 单条结果的文本内联预算（字符）。默认值由真实语料扫描确定（`tools/sweep2.mjs`） |
| `triggerRatio` | `1` | 超过 `inlineChars × triggerRatio` 才裁剪；预留安全带会减少改动面但省量下降，实测无收益 |
| `headRatio` / `tailRatio` | `0.55` / `0.35` | 头部 / 尾部占比 |
| `minTailChars` | `300` | 尾部最少保留字符数，保证可恢复路径不被切掉 |
| `importantBudgetRatio` | `0.4` | 可疑行预算占比（实际额度不低于 400 字符） |
| `toolBudgets` | `{}` | 工具级预算覆盖，例如 `{ read: 4000 }` |
| `skipTools` | `[]` | 完全跳过的工具（连无损规范化都不做） |
| `logSavings` | `false` | 把每条省量写进 Host 日志 |

### 分工具预算的实测取舍（2596 条真实结果）

`bash` 的结果可以用同一条命令重跑取回，所以它的预算可以比 `read` 更紧。实测：

| 配置 | 压缩后 token | 相对默认再降 | 被裁剪条数 |
|---|---:|---:|---:|
| 默认（全工具 1600） | 388,740 | — | 625 |
| `{ bash: 1000 }` | 327,133 | **−15.9%** | 808 |
| `{ bash: 800 }` | 298,634 | **−23.2%** | 902 |
| `{ bash: 600 }` | 272,873 | **−29.8%** | 1,019 |
| `{ read: 2400 }` | 406,868 | +4.7%（更贵） | 611 |

代价是**更多结果被裁剪**：模型需要重跑命令才能看到被省略的中段。默认保持 1600，是因为
"质量不变"的证据只覆盖这个取值；要更省就显式下发 `toolBudgets` 并接受该取舍。

只读统计面：`ctx.toolTokenOptimizerStats.snapshot()`
→ `{ calls, optimized, tokensBefore, tokensAfter, elided, lossless }`。

**配置校验零依赖**：`Config` 用包内自带的 Standard Schema v1 实现（`lib/schema.js`）。
不用 `zod` 是刻意的——profile 侧插件解析不到 `zod`（本机已核实，官方 `dsh-session-cost`
也因此自带 schema）；未知配置键、越界取值都会在装配时被拒绝并给出确切字段。

## 10. 安全边界

- 只读工具结果，不写文件、不发网络请求、不改会话日志；
- 任何内部异常都被吞掉并记 `warn`，工具调用本身不受影响（有专门用例）；
- 全程确定性：同样的输入永远得到同样的输出，不引入任何抖动。

# A/B 对照实验：裁剪到底会不会影响模型的结果

这是插件唯一没法用"信息守恒"证明的问题：**信息可恢复 ≠ 模型会去恢复**。
这里用真实模型、真实工具、客观可判分的任务做了三组对照。

## 实验设计

固定材料：`.ab-test/registry.txt`（300 行、22,058 字符），每行 `ITEM-NNN value=<n*1000+7> owner=... note=...`。

| 组 | 配置 | 任务 | 唯一变量 |
|---|---|---|---|
| 对照 | `inlineChars: 100000000`（插件在跑但不裁剪） | 读出所有 `value % 7 === 0` 的条目 | — |
| 实验 | `inlineChars: 1600`（默认，裁剪中段） | 同上 | 裁不裁中段 |
| 实验·仅读一次 | 同实验组 | 找中段里的"针"，且**限定只能 read 一次、禁止命令行** | 是否强制依赖那一份结果 |
| 实验·允许取回 | 同实验组 | 同"针"任务，但**允许按说明用 offset/limit 分段读完** | 取回路径是否可用 |

"针"的定义：文件第 149 行埋 `NEEDLE-TOKEN=X7Q9-DEEP-MIDDLE`。按默认预算复算，插件保留的是**前 ~35 行 + 后 ~21 行**，第 149 行必定落在被省略的中段。

## 结果

### 第 1 组：真实任务（"把 300 行里所有满足条件的条目全部列出"）

| | 对照（不裁剪） | 实验（裁剪） |
|---|---|---|
| **最终答案** | COUNT=42，42 个 ID | COUNT=42，**逐项一致** |
| 判分 | **42/42 正确** | **42/42 正确** |
| 请求数 | 4 | 5 |
| 工具结果数 | 3 | 4 |
| prompt token | 68,942 | **60,980（−11.6%）** |
| 缓存命中率 | 87.3% | **98.2%** |

**结论：答案没有任何差别。** 实验组为了严谨，多跑了一次 bash 去独立复核（它没有信任被裁剪的 read 结果），所以工具调用数 +1、token 优势被摊薄——但它**没有因为裁剪而答错或漏项**。

### 第 2 组：强制依赖那一份结果（"针"任务，只许 read 一次）

| | 结果 |
|---|---|
| 最终答案 | `NOT_VISIBLE 我看到的行号范围是 1-9, 295-300` |
| read 调用 | 1（遵守限制） |
| bash 调用 | 0（遵守限制） |
| 裁剪说明 | `[…] omitted 22365 chars / 287 lines of 23624; re-read with offset/limit to see any range` |
| 正确答案 | `FOUND LINE=149 TOKEN=X7Q9-DEEP-MIDDLE` |

**结论：信息确实被延后了。这一步不遮不掩——单纯只看那一份被裁剪的结果，中段的内容是拿不到的。**

### 第 3 组：允许按说明取回（同一个"针"任务）

| | 结果 |
|---|---|
| 最终答案 | **`FOUND LINE=149 TOKEN=X7Q9-DEEP-MIDDLE`** |
| read 调用 | **30 次，全部带 offset/limit** |
| bash 调用 | 0 |
| prompt token | 105,329 |
| 缓存命中率 | 89.8%（30 次追加，命中率被自身未命中摊薄） |

**结论：取回路径真的会被用起来，而且答案完全正确。** 代价是这条任务里模型选择了"按 30 行一小段读完整个文件"，累计 105k token——**比对照组的 68.9k 更贵**。

## 怎么解读

1. **对"不需要中段"的任务（绝大多数真实场景）：没有可测量的质量差异。** 第 1 组答案逐项一致，且实验组更省。
2. **对"中段里正好有唯一答案"的任务：会多付一次取回成本。** 第 3 组就是这种情况，而且因为模型选择了小段反复读，这次取回比"原本一次读全"更贵（105k vs 68.9k）。
3. **所以插件的真实代价不是"答错"，而是"偶发的额外取回"，且取回可能不便宜。** 这与我在设计里的假设（"取回很便宜"）**不完全成立**——这是本次实验最有价值的发现。

## 由此得到的改进方向（尚未实施）

- 当**整份结果都被裁剪**（而不是只切掉一段）时，"重读整份"往往比"按 30 行分段"更省。说明行可以据此给出更精确的建议，或插件对"单块纯文本且超预算 3 倍以上"的结果采用更宽的预算。
- 可以给 `read` 单独设 `toolBudgets`（例如 4000 字符 ≈ 80 行），让中段缺口更小，降低触发取回的概率。

这两条都需要再跑一轮对照才能确认收益，因此我**没有**擅自改默认值。

# 第二轮：8 任务 × 2 条件的正式对照（自动判分）

第一轮只有 1 个任务、还被"模型自行换路"污染。这一轮补齐：**8 个任务、两个条件、共 16 次真实运行**，
判分完全由 `tools/ab-score.mjs` 按 `answer-key.json` 自动完成。

## 材料与任务（全部在 `.ab-fixtures/`，由 `tools/ab-fixtures.mjs` 生成）

| 任务 | 类型 | 标准答案 |
|---|---|---|
| T1-divisible7-count | 全文件提取计数 | 57 |
| T2-divisible7-list | 全文件枚举（57 项） | 57 个 ID |
| T3-needle-alpha | **中段唯一信息**（第 137 行埋针） | Q7X2-M9 |
| T4-needle-beta | **中段唯一信息**（第 291 行埋针） | Z3P8-K4 |
| T5-mid-warn-count | 中段为主的枚举计数 | 67 |
| T6-distinct-error-codes | 去重计数 | 200 |
| T7-head-error-count | 头部枚举计数 | 67 |
| T8-owner-team-5-count | 条件计数（全文件） | 34 |

两个文件各含**干扰行**（`ITEM-137` / `ITEM-291` 缺少 `value=` 字段），
用 `awk $2%7` 这类粗暴解析会得到 59 而不是 57 —— 这是刻意的"陷阱"，用来分辨真读还是猜。

## 结果

| 任务 | 对照（插件关闭） | 实验（插件启用） |
|---|---|---|
| T1 | ✔ 57 | ✔ 57 |
| T2 | ✔ 57 项 | ✔ 57 项 |
| T3 | ✔ Q7X2-M9 | ✔ Q7X2-M9 |
| T4 | ✔ Z3P8-K4 | ✔ Z3P8-K4 |
| T5 | ✔ 67 | ✔ 67 |
| T6 | ✔ 200 | ✔ 200 |
| T7 | ✔ 67 | ✔ 67 |
| T8 | ✔ 34 | ✔ 34 |
| **正确率** | **8/8（100%）** | **8/8（100%）** |

**两条件逐题判定完全一致，包括两道"答案只存在于被省略中段"的针任务。**

## 成本（prompt token）

| | 对照 | 实验 | 差 |
|---|---|---|---|
| prompt 合计 | 474,066 | 537,214 | **+13.3%** |
| 请求数 | 40 | 45 | +5 |
| bash / read / grep | 18 / 5 / 3 | 24 / 2 / 3 | read↓ bash↑ |

逐题差异极大：T2 **−31%**、T5 −0.7%、T3 −0.3%，但 T1 **+54%**、T7 **+45%**、T6 +17%。

**必须说清楚：这一栏不能当作结论。** 每个任务只跑了 1 次，单任务方差就有 ±30% 量级，
合计 +13% 完全可能是噪声。要判定成本方向，需要每任务 3–5 次重复。

## 结论

1. **质量维度：8/8 对 8/8，包括两道中段针任务，没有观察到任何质量差异。** 针任务能过，
   是因为模型自己选择了 `grep`/`bash` 另一条路径，或按说明续读 —— 这正是真实会话里的行为。
2. **成本维度：`+13%` 不显著，但也不支持"必然更省"的强主张。** 与第一轮"整份被裁剪时取回可能更贵"
   的发现方向一致，都指向同一个未解决的问题：**对"中段里正好有唯一答案"的任务，插件可能让整体更贵。**
3. 因此默认值仍维持 `inlineChars: 1600`（在真实语料上省 62.8% 的工具结果 token），
   但**没有**把"成本必然下降"写进任何主张里。

## 复现

```bash
node tools/ab-fixtures.mjs .ab-fixtures          # 生成材料与标准答案
# 切换条件（改 profile 的 cordis.patch.yml 后重启），各跑 8 个子代理
node tools/ab-score.mjs .ab-run/control.json .ab-run/treatment.json --fixtures .ab-fixtures
```

# 第三轮：成本证据（5×2 重复，口径修正）

## 先纠正一个错误口径

第二轮我报过"实验组 prompt 合计 +13.3%"，**那个算法是错的**：两个条件的**请求数不同**
（40 vs 45），而 prompt token 合计 = Σ(每次请求的整段上下文)，缓存命中部分会**按请求数重复计入**。
把不同请求数的总量直接相加，比较的是"跑了多少请求"，不是"插件省不省"。

**正确口径有两个**：① 每次请求的**新增**（未命中）token；② 按 provider 单价折算的总成本。

## 第二轮的同一批数据，换正确口径重算

| 口径 | 对照 | 实验 | 结论 |
|---|---|---|---|
| 请求数 | 40 | 45 | +5（其中 **3 次出现在根本没发生裁剪的任务上**，与插件无关） |
| 未命中输入 | 12,882 | 9,982 | **−22.5%** |
| **未命中 / 请求** | **322** | **222** | **−31.1%** ← 这才是插件的作用点 |
| 按价折算成本 | ￥0.0221 | ￥0.0205 | **−7.1%** |

"多余请求与裁剪无关"的正交性检验：有裁剪的 4 个任务请求数变化合计 +2，无裁剪的 4 个任务 +3。
**多数波动来自运行间随机性，不是裁剪造成的。**

## 第三轮：专门为"成本"设计的 5×2 重复实验

材料同构、只差规模（`tools/` 未包含生成物，见下方复现命令）：

| | small | large |
|---|---|---|
| 内容 | 200 行 / 14,832 字符 | 2,400 行 / 183,186 字符 |
| 规模比 | 1× | **12.4×** |
| 是否触发裁剪 | 否（单次结果小于预算） | **是** |
| 标准答案 | 28 | 342 |

各跑 5 次，结果：

| 指标 | small（5 次） | large（5 次） | 变化 |
|---|---|---|---|
| 请求数均值 | 5.0 | 5.2 | +4%（噪声级） |
| 未命中输入均值 | 1,720 | **1,273** | −26% |
| 命中输入均值 | 57,011 | 59,085 | +3.6% |
| **未命中 / 请求** | **344** | **245** | **−29%** |
| 按价折算成本 | ￥0.00286 | **￥0.00245** | **−14%** |
| 正确率 | **5/5** | **5/5** | 无差异 |

**结论：内容规模放大 12.4 倍，prompt 成本反而降到 0.86 倍；未命中输入只放大 0.74 倍。**
若不裁剪，183K 的结果会随每一次后续请求重发（14 次里 4 次），这一项会按规模线性放大；
实测它没有放大，反而更小 —— 这正是插件设计的直接效果。

## 复现

```bash
node tools/ab-fixtures.mjs .ab-fixtures        # 任务材料
# 成本实验材料（同构、只差规模）：
node -e '
const {writeFileSync}=require("fs");const mkdir=(p)=>require("fs").mkdirSync(p,{recursive:true});
mkdir(".cost-ab");
for (const [n,f] of [[200,".cost-ab/small.txt"],[2400,".cost-ab/large.txt"]]) {
  const L=[];for(let i=1;i<=n;i++)L.push(`ITEM-${String(i).padStart(4,"0")} value=${i*1000+7} owner=team-${(i%12)+1} note=record number ${i} of the registry`);
  writeFileSync(f,L.join("\n")+"\n");
}'
bash dsh-tool-token-optimizer/tools/run-cost-ab.sh    # 见下：需要外部批量派生 5×2 个子代理
```

> 说明：子代理的批量派生必须由持有 `subagent` 工具的 agent 完成（bash 里没有这个工具），
> 因此这一步无法完全脚本化；判分与计量用 `node tools/session-metrics.mjs <id>`。
